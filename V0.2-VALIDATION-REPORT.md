## 4. Collector Fixes Found by Live Testing

These are bugs the tests found, not bugs I anticipated.

### RELIABILITY-1 (critical) — one failed delivery permanently disabled the collector
`flush()`, `send_test_event()`, `run_connection_test()` and `Heartbeat::send()` all gated on
`is_connected()`, which requires `state === connected`. But `record_failure()` sets state to
`error`. So **the first failed POST disabled delivery and the heartbeat forever** — the queue
never drained even after ScanSite recovered, and the connection could never self-heal.
**Fix:** added `ScanSite_BB_Connection::has_credentials()` (site ID + key + endpoint only) and
gated all four delivery paths on it. State remains a reporting signal, not a switch.
Proven by the offline test: 5 events queued during an outage, then **5/5 delivered after
recovery** with state returning to `connected`.

### CRON-1 (critical) — the collector broke every scheduled event on the site
`schedule_event` is an `apply_filters` call in core (`wp-includes/cron.php:179`, `:287`) followed
by `if ( ! $event ) return false`. The collector used `add_action` and returned `null`, so
**every `wp_schedule_event()` site-wide returned `false`** — including the collector's own flush
and heartbeat cron. **Fix:** `add_filter` + `return $event`.

### CRON-2 — `cron_removed` never fired
No `unschedule_event` action exists in core. **Fix:** `add_filter('pre_unschedule_event', …, 10, 5)` returning `$pre`.

### Duplicate `administrator_created`
`wp_insert_user` fires `set_user_role` with `old = []` *before* `user_register`, so one creation
emitted two events. **Fix:** guard on `empty( $old_roles )`.

### Login-failure spam
10 failed attempts produced 10 events. **Fix:** aggregation window → 4 events (3 individual + 1 burst).

### `plugin_deleted` lost the plugin name
The name is unresolvable once the row is gone. **Fix:** snapshot on `delete_plugin`.

### Upgrader metadata was unavailable
`$upgrader->skin->plugin_info` and `$upgrader->new_plugin_data` **do not exist in WordPress 6.8**.
**Fix:** snapshot old versions via the `upgrader_package_options` filter; derive a fresh install's
folder from `$upgrader->result['destination_name']`.

### Two ScanSite-side fixes
- `ingest.js` silently dropped per-event rejections on partially successful batches. Now reported,
  so a collector that sent one malformed event alongside good ones can see it.
- The collector download route used a **hardcoded 7-file manifest** and was shipping a ZIP
  **without `class-diagnostics.php`** — activating it would fatal. The manifest is now derived from
  disk. Verified: ZIP contains all 8 files.

## 6. Raw Event Explorer

**Route:** `/websites/[id]/events` (in the build's route table) · **API:** `/api/blackbox/events`
· linked from the website detail page as "View Raw Events →".

- **Header:** matching event count, collector status, last refresh
- **Filters:** search (plugin / username / path / IP / event ID), category, event type, actor —
  driven by server-computed facets with counts
- **List:** time, type, human description, actor, IP, eventId, incident severity badge
- **Detail:** category, UTC timestamp, actor + role, IP, target, old→new change, path, **correlation
  counts** (same actor / same IP / same plugin / same incident), **incident link**, and
  **View Raw Payload** as formatted JSON
- **Refresh:** 8-second polling — no WebSockets, no Redis
- **Pagination:** Load More, 50 per page

Verified live: `GET /api/blackbox/events?site=…&q=cron&correlation=1` → total 76, facets returned,
correlation `{sameActor: 115, sameIp: 115, samePlugin: 0, sameIncident: 117}`, incident linked.
Page returns HTTP 200.

## 7. Privacy Review

Real payloads captured from WordPress, scanned for 17 secret patterns across 1,029 bytes: **0 hits**.

- `.htaccess` / `wp-config.php` changes send **sha256 only** — contents never transmitted
- Executable-file events send path, extension, size, permissions and a hash — **no file contents**
- Cron events send `schedule` / `nextRun` / `argCount` / `argsHash` — **raw args never sent**
  (`argCount=2 argsHash=d7acc8a4c641`)
- Option monitoring uses an **allowlist**, not blanket `option_changed`
- **Spoofed `X-Forwarded-For` / `X-Real-IP` are ignored**; recorded IP is `REMOTE_ADDR` (`203.0.113.9`)
- The collector key never appears in diagnostics, admin HTML or event payloads

## 9. Reliability, Batching, Payload Contract

- **Queue cap 1000.** Enqueuing 1005 keeps indices 5…1004 — **policy: drop oldest, keep newest**.
- **Offline:** 5 events stayed queued, attempts incremented, message *"ScanSite could not be
  reached from this website."* (no stack trace). After recovery **5/5 delivered, state `connected`**.
- **Batching at 50:** 73 queued → 23 after one flush → 0 after two; **73/73 arrived**.
- **Partial batch:** one malformed event alongside good ones does not fail the batch.
- **Vocabulary cross-check:** the collector emits **32** event types; **32/32 accepted** by ScanSite.

- **Payload contract:** `schemaVersion: 1` on every event · timestamps ISO-8601 UTC
  (`2026-08-27T18:12:38+00:00`) on both sides · eventIds unique.

## 14. Remaining Limitations

- The dashboard has **no authentication** (per spec). It is a local diagnostic tool, not a
  multi-tenant product.
- JSON file storage caps at 5,000 events / 1,000 incidents; there is no cloud database by design.
- Rotate Key does not auto-sync to the collector — an administrator must re-enter the code.
- The SQLite drop-in used by the lab is **not** part of the shipped plugin.
- Diagnostics' outbound-HTTP check fails in this sandbox because outbound HTTPS is blocked; on a
  normal host it should pass.

**This is not "production ready".** What is demonstrated is narrower and more specific: on a real
WordPress 6.8.3 installation, the collector detects 27 event types accurately, queues and delivers
them reliably across an outage, leaks no secrets, and produces incidents whose evidence traces back
to real events.
